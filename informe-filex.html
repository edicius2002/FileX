La mitad que no acelera

571 000 líneas de Java sin una sola llamada a CUDA

Stirling-PDF, ConvertX, VERT, transmute, gotenberg y morphos suman cero ficheros con CUDA o NVENC. Convierten vídeo con FFmpeg ya integrado y no piden la GPU ni una vez.

La mitad que sí acelera

Docling, Surya, Marker, MinerU y faster-whisper viven en la GPU

Entre 5 y 37 ficheros con CUDA cada uno, selección de dispositivo, control de precisión y tamaños de lote. Pero ninguno convierte un MP4 ni redimensiona un PNG: solo hacen documento a texto.

Único cruce, y a medias

SnapOtter (creado hace cinco meses, 100+ commits al mes) es el único proyecto que cruza la línea: acelera eliminación de fondo, upscaling y transcripción. Pero su OCR está bloqueado en CPU por diseño, no tiene MCP ni CLI, y su núcleo comercial exige licencia de pago.

Tres hallazgos que solo aparecen leyendo el código

Los metadatos de GitHub y los README dicen otra cosa en los tres casos.

ConvertX elige siempre el conversor equivocado

Su despachador recorre 20 motores buscando cuál soporta el par origen–destino. El break rompe el bucle interno, nunca el externo:

for (converterName in properties) {          // bucle EXTERNO
  for (const key in converterObj.properties.from) {
    if (from.includes(fileType) && to.includes(convertTo)) {
      converterFunc = converterObj.converter;
      break;                                // rompe SOLO el interno
    }
  }
}                                            // el externo sigue: gana el ÚLTIMO

El orden del registro es prioridad declarada —el código lleva un comentario «Prioritize Inkscape for EMF files»— pero funciona como prioridad inversa. Para png→jpg coinciden vips, ImageMagick, GraphicsMagick y FFmpeg; gana FFmpeg, el peor de los cuatro para imagen fija. Y como converterName es la variable del bucle, al terminar vale la última clave del registro: el log dice casi siempre markitDown, sea cual sea el motor real.

SnapOtter rechaza activamente su propio OCR en GPU

No es un valor por defecto conservador: es una validación que lanza excepción si el runtime reporta cualquier dispositivo que no sea CPU.

function validateReadinessResult(result, runtime) {
  if (
    ...
    result.device !== "cpu" ||            // rechaza cualquier resultado en GPU
    ...
  ) throw new Error("Accurate OCR runtime returned a malformed readiness result");
}

Su README lo confirma: «OCR deliberately uses the same portable CPU runtime on CPU-only and NVIDIA hosts». Priorizan reproducibilidad sobre velocidad. Su transcripción, además, empaqueta solo faster-whisper-small para no inflar la imagen Docker.

El líder del mercado ya construyó MCP — y lo puso detrás de una suscripción

La API de GitHub reporta que Stirling-PDF no tiene MCP. El repositorio dice lo contrario: hay un servidor MCP completo con catálogo de herramientas, ejecutor, filtro de clave de API y configuración de seguridad. Vive en app/proprietary/, uno de los diez directorios excluidos del MIT del repositorio, bajo una licencia que exige suscripción para uso en producción.

Esto reencuadra el hueco: no es que nadie lo haya pensado, es que quien lo pensó lo está monetizando. Valida que el ángulo vale dinero y advierte de que la ventana no es infinita.

La idea que sí merece copiarse

Su McpToolCatalog no declara herramientas a mano: escanea los endpoints REST existentes y los publica como herramientas MCP, excluyendo los verbos destructivos. En FileX, el catálogo MCP debe generarse desde el registro de conversores: un motor nuevo aparece como herramienta sin tocar la capa MCP.

Salvedad honesta

El agujero que nadie menciona: ConvertX no convierte hojas de cálculo

Búsqueda de xlsx, xls y ods en sus 20 adaptadores: cero apariciones, ni como entrada ni como salida. Tampoco ppt ni odp. La causa está en libreoffice.ts, que registra únicamente la familia text: pese a que el binario soffice al que llama convierte hojas de cálculo y presentaciones sin problema.

NVENC: qué acelera y qué no

Corrección sobre la primera versión de este informe

Publicó 3,3× para H.264 a partir de una única ejecución sin calentamiento. Con n=9 la cifra real es 2,7–3,0×. El hallazgo grande estaba en otro sitio: HEVC rinde 8,4×, porque hevc_nvenc cuesta lo mismo que h264_nvenc mientras libx265 es 3× más lento que libx264. Para FileX, HEVC es la salida donde la GPU se paga sola.

El coste que casi nadie mide: NVENC se pasa de bitrate

La pérdida de calidad a igual bitrate es pequeña, pero NVENC no respeta el bitrate objetivo. A 2 Mbps entrega 2 214 kbps (+10,7 %) frente a los 2 026 de x264 (+1,3 %). El patrón se repite en los tres puntos medidos.

Traducción para FileX: si el usuario pide «comprime este vídeo a 2 Mbps», NVENC devuelve un fichero un 10 % más grande de lo pedido. El grafo debe contabilizarlo como coste de la arista, no tratar CPU y GPU como equivalentes.

La tubería GPU completa no sirve

Decodificar también en GPU con -hwaccel cuda -hwaccel_output_format cuda para evitar la copia de memoria no aporta nada: entre −13 % y +3 %, dentro del ruido. Y con escalado es un 34 % peor que decodificar en CPU.

Corrección: la primera versión de este informe afirmaba que «con decodificación también en GPU la ventaja crece». Era una suposición, no una medición, y es falsa.

Regla de diseño derivada

Las capacidades se sondean en ejecución y se cachean, nunca se deducen de la lista de codificadores del binario. Un av1_nvenc fallido debe degradar solo a libsvtav1 en CPU.

Arranque en frío: la medición que cambia la elección de lenguaje

Media de 25 ejecuciones tras calentamiento. El calentamiento importa: sin él, Windows Defender inflaba el binario Go recién compilado de 41 ms a 110 ms.

Go compilado41 ms
cmd /c exit (suelo)49 ms
Python desnudo60 ms
ffmpeg -version61 ms
magick (PNG 64×64)73 ms
Node.js74 ms
Python + stdlib85 ms
  • En Windows, crear un proceso cuesta ~49 ms haga lo que haga. Es el suelo, y no depende del lenguaje.
  • Elegir Go en vez de Python ahorra ~44 ms por invocación. Real, pero modesto.
  • Cualquier conversión arranca además un motor externo: FFmpeg cuesta 61 ms solo en existir; ImageMagick 73 ms para un PNG de 64×64, de los cuales apenas 30 ms son trabajo útil.
  • Para el servidor MCP el arranque en frío es irrelevante: el proceso arranca una vez y permanece vivo.
Conclusión

El lenguaje del núcleo controla ~40 ms de una invocación de 100–160 ms, y solo en la CLI. El argumento «Rust por el arranque» queda muy debilitado. La palanca real no es el lenguaje: es evitar procesos, manteniendo vivos el sidecar de IA y los motores caros.

Trampa 1 · silenciosa

pip install surya-ocr destruyó la instalación CUDA

Degradó torch de 2.6.0+cu124 a 2.13.0+cpu sin un solo error. Todo habría seguido corriendo, en CPU, sin que nada lo delatara. FileX debe verificar torch.cuda.is_available() en cada arranque del sidecar y negarse a anunciar aceleración que no tiene.

Cómo leer esas aceleraciones

Los múltiplos grandes engañan. RapidOCR «solo» gana 3,5–4,2× porque su ruta en CPU ya es la más rápida (763 ms frente a los 6 660 ms de EasyOCR). Comparando el mejor CPU contra el mejor GPU, la ganancia real del ecosistema es 3,9×, no 17×. Un motor lento que se acelera mucho sigue siendo un motor lento.

La elección es RapidOCR con backend="torch": reutiliza el torch ya instalado, así que su coste de infraestructura GPU es cero —ni onnxruntime-gpu, ni paddlepaddle-gpu, ni ruedas de runtime CUDA— y su salida es idéntica carácter a carácter a la de CPU. PaddleOCR es más preciso (0,0 % de CER) pero cuesta 3,73 GB, un segundo entorno virtual aislado y 24,8 s de carga: queda como ruta opcional de máxima precisión. EasyOCR se descarta: peor precisión y resultados no deterministas entre CPU y GPU en entradas degradadas.

En la dificultad 3 fallan los tres (57–76 % de CER). Es un límite honesto: el OCR acelerado resuelve documentos degradados, no documentos destruidos.

Bug ajeno · docling 2.120.3

Rellena dos de los tres use_cuda

Configura EngineConfig.paddle.use_cuda y EngineConfig.torch.use_cuda pero olvida EngineConfig.onnxruntime.use_cuda, que es justo el backend por defecto. Aun con la CUDA EP funcional, Docling seguía haciendo OCR en CPU. Se sortea con rapidocr_params, pero es un motivo más para preferir el backend torch.

Whisper: dónde está el umbral entre los dos modelos

distil-large-v3 empata con large-v3 (WER 0,00 %) en clips de 11 segundos, incluso con ruido blanco añadido y en banda telefónica de 8 kHz. Pero en un audio de 308 segundos produce 4,4–4,6 % de WER: duplica y se salta fragmentos en las costuras de las ventanas de 30 s, y devuelve 29 arranques de frase donde había 28. large-v3 clava 28 de 28 en ambas condiciones.

Regla para FileX: distil-large-v3 hasta 30 segundos, large-v3 por encima. Ahorra 2 678 MiB de VRAM en el caso corto sin perder nada.

Corrección interna entre fases

La fase 1 midió Docling en frío y concluyó que la GPU aportaba poco, recomendando enrutar los PDF pequeños a CPU. En caliente, la GPU aporta 5,6–6,4× en maquetación. Esa recomendación se contradecía consigo misma —el sidecar residente que la propia fase 1 propone mantiene los modelos calientes— y queda anulada: todo va a GPU.

Perfil completo conviviendo —whisper large-v3 residente, Docling con OCR en GPU y NVENC simultáneos—: pico de 7 702 MiB con 4 586 libres, sin degradación del OCR. Cabe entero en la 3060 con margen.

Licencias: por qué transmute es la única base viable

Casi todo el terreno con tracción es AGPL. La decisión conviene tomarla ahora, porque no cuesta más trabajo.

Invocar un binario como proceso separado no contamina. Enlazar una librería GPL dentro de tu programa obliga a publicar tu programa como GPL; ejecutar ffmpeg entrada.mp4 salida.webm como proceso externo, no. Por eso todos los conversores serios son orquestadores de procesos —ConvertX usa execFile sin shell en todos sus adaptadores— y por eso FileX debe serlo también: preserva todas las opciones de negocio sin coste técnico, y además es inmune a inyección de shell.

La pista de audio: predicho y confirmado

La referencia nativa había establecido que ffmpeg -i entrada.mkv salida.mp4 descarta la segunda pista de audio en silencio por selección de flujos por defecto, y que con -map 0 se conservan ambas. MP4 admite varias pistas: es fallo de uso, no del formato.

Los dos competidores caen exactamente en ese fallo, y los dos reportan éxito. Envuelven FFmpeg sin -map 0. Es el hueco más claro que comparten.

Y el dasel de ConvertX está roto

Se invoca con sintaxis de la versión 1 (--file) contra un binario de la versión 2. Todas sus conversiones de datos son inalcanzables, no solo el CSV del corpus. Un adaptador declarado, contado en la matriz de formatos, y muerto en ejecución.

La regla de diseño que sale de aquí

FileX necesita un contrato de verificación obligatorio después de cada conversión: firma real del fichero, flujos esperados frente a obtenidos, y propiedades declaradas frente a medidas. Los tres fallos más graves de esta comparativa —el AVIF que era PNG, la pista perdida y las degradaciones de bits, ppp y bitrate— los habría atrapado los tres.

Con su corolario, que es menos obvio: un recurso alternativo sin verificación es peor que no tenerlo, porque convierte un fallo honesto en uno silencioso. Es literalmente lo que le pasa a ImageMagick dentro de ConvertX.

Método: 96 invocaciones reales, todas en serie sobre una VM de 2 vCPU · los tiempos solo comparan un competidor con el otro, nunca con los nativos · la dispersión llega a 9,2× en la misma conversión, así que toda diferencia menor de ~2× es ruido · el arranque en frío domina hasta 53× entre la primera llamada y la segunda.

08

La decisión

Híbrido asimétrico: desde cero el núcleo, reutilizando todo lo demás.

Ningún candidato sirve como base tal cual. SnapOtter es AGPL con CLA y avanza a 100 commits al mes: un fork en solitario es insostenible. ConvertX es AGPL y su despacho es justo lo que hay que rehacer. Stirling-PDF es solo PDF, en Java, con el MCP de pago. VERT y morphos están parados. Gotenberg no es un conversor universal, es una dependencia excelente.

Queda transmute, MIT y bien estructurado — pero es una API web sin CLI, sin MCP, sin watcher y sin GPU. Adoptarlo entero obligaría a arrastrar su frontend y su capa k8s cuando FileX es local-first. Lo que sí se toma es su núcleo conceptual, probado y permisivo: el registro por reflexión con can_register(), la ConverterInterface, y adaptadores de nicho que nadie más tiene (fuentes tipográficas, subtítulos, datos tabulares, correo).

Lo que hay que escribir de cero es exactamente lo que nadie tiene.

Proceso único y persistente. El MCP arranca una vez, así que los 44 ms que ahorraría Go no se cobran donde importa.
registro + grafo de conversión
Nodos = formatos · aristas = (motor, coste) · Dijkstra elige el camino. Auto-descubrimiento con can_register(): en tu máquina hay 4 de los ~12 motores, así que arrancar con capacidades reducidas es requisito, no detalle.
motores externos — execFile, sin shell
ffmpeg · magick · soffice · pandoc · calibre · vips · qpdf. Frontera de proceso: sin contaminación GPL, sin inyección, fallos aislados.
sidecar IA — proceso Python aparte
docling · surya · faster-whisper large-v3. Modelos residentes en VRAM con descarga por inactividad. Separado porque torch y CUDA reservan enormes cantidades de espacio virtual: el mismo motivo que llevó a SnapOtter a aislarlo.

Por qué Python y no Go o Rust

  • El ecosistema que importa es Python. Docling, Marker, Surya, faster-whisper, PyMuPDF, Pillow, DuckDB. El cuarto diferenciador entero vive ahí; desde Go o Rust se accede por IPC, con coste y sin ganancia.
  • La base reutilizable ya es Python y es MIT.
  • El sidecar separado no es opcional en ningún lenguaje. Ese problema existe igual con un núcleo en Go.
  • La deuda es acotada. Si algún día molesta el arranque de la CLI, se reescribe el despachador —unos cientos de líneas— en Go, dejando intactos el sidecar y los adaptadores.

Go sigue siendo defendible si la prioridad real fuese distribuir un binario único sin dependencias. Pero eso choca con el sidecar Python, que hay que instalar de todos modos para OCR y transcripción.

Orden de construcción

  1. Registro, grafo y CLI con FFmpeg e ImageMagick — 76 % de la cobertura de formatos con dos motores.
  2. NVENC con sondeo de capacidades y degradación a CPU. 3,3× medido, coste casi nulo.
  3. Capa MCP generada desde el registro, devolviendo ruta y metadatos —nunca contenido—, con readOnlyHint/destructiveHint y caché idempotente por hash.
  4. Gotenberg en Docker para ofimática a PDF, evitando instalar LibreOffice en Windows.
  5. Sidecar IA: faster-whisper (distil-large-v3 hasta 30 s, large-v3 por encima) y Docling con RapidOCR en backend="torch", que da OCR en GPU sin infraestructura añadida. PaddleOCR queda como ruta de máxima precisión, en su propio venv.
  6. Watcher y API HTTP local, que a esas alturas son superficies delgadas sobre el mismo núcleo.

Los pasos 1 y 2 ya superan en cobertura y velocidad a todo lo analizado, salvo en OCR y ofimática.
